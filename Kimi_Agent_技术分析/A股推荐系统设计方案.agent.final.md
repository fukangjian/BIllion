# 职业投资自动化A股推荐系统设计方案

> 版本：v1.0　|　日期：2026-07-31　|　性质：个人自用技术设计文档（非投资建议）

---

## 第1章 项目概述与总体架构

### 1.1 背景与痛点

本项目的发起人是一名A股散户：本金约3.25万元，具备Python、嵌入式、n8n与钉钉机器人的工程能力，职业目标为3年内成为基金经理。其已手写形成一套事件驱动短线交易体系，并在2026年7—8月实盘中验证了体系本身的有效性——严格按体系执行的4笔交易全部盈利（山东墨龙+8.1%、创新医疗+6.5%等，总胜率4/6，累计约+2674元）。问题在于：**亏损几乎全部来自执行层失误而非逻辑层错误**。复盘其2026年7月实盘笔记，可归纳出5类反复出现的问题。

第一类是**情绪操作**。通源石油12.05元卖出后，当日12.20元高接追回，单笔追价成本-210元；7月30日被9:15—9:30集合竞价洗盘吓卖，笔记自评"临时决策未看本笔记（失败）"，该笔亏约10%。这类失误的特征是盘中冲动覆盖盘前计划。

第二类是**早盘时间窗约束**。其成交几乎全部集中在09:25—09:56（上班前半小时），曾因同事在旁紧张操作出错。这决定了系统必须在9:15之前把当日交易计划推送到手边，盘中再无时间做分析。

第三类是**挂价与网络失误**。开盘价上浮5%的卖单因挂低1分钱未成交；家中WiFi延迟导致卖单提交失败。这类低级失误对应明确的工程对策（挂价规则、5G备用链路），纯属"不该发生但反复发生"的损耗。

第四类是**信息过载与纪律失效**。信息渠道分散在东方财富、同花顺、股吧，笔记自记"心态不好时不看评论区"，又曾因忘记看板块排行榜而错过一鸣食品与传智教育——信息过载导致该看的信息漏看；违规买入创业板壹连科技，次日集合竞价卖出，-3.9%；笔记中反复出现"操作前，先写下买点和卖点"的自我提醒，说明纪律依赖自觉、缺乏强制机制。系统对此的回应是收敛信息渠道、以观察池管理标的、自动监控板块排行榜，并把纸面纪律改造为强制机制。

第五类是**复盘缺失**。笔记自评"积累二三十个案例……建立交易体系比单纯研究技术指标提升更快"，方向明确，但手写复盘难以坚持，案例库始终停留在纸面。

这5类问题的共同特征是：都可被规则化、自动化、强制化。这正是本项目的切入点——不重造交易逻辑，而是把已验证有效的体系工程化，消灭执行层失误。

### 1.2 设计目标与边界

系统定位为**纯自用的"信号推荐+纪律执行辅助"系统**，目标不是预测涨跌，而是把手写体系升级为系统：盘前自动产出当日计划与候选股评分，盘中按预设纪律监控持仓，盘后自动复盘归档。设计边界共三条，必须先行声明。

其一，**现阶段不做全自动下单**。券商官方量化终端QMT的最低可验证资金门槛为10万元（国金证券），本金3.25万元不满足（来源：licai.cofool.com，2026-06），因此执行通道以券商APP条件单半自动+人工确认为主，信号层与执行层解耦，保留未来升级miniQMT乃至全自动的插拔能力。

其二，**合规边界一句话**：系统仅供本人使用，不对外推送、不收费、不建群；使用自研软件进行程序化交易需向券商履行报告义务，但个人低频交易远未触及高频标准（300笔/秒），实质影响极小（详见第6章）。

其三，**能力边界**：系统输出的是"建议+纪律约束"，最终下单决策与资金安全仍由本人负责；数据全部来自公开免费/低成本渠道，不使用任何内幕或付费Level-2以上数据。

### 1.3 总体架构

系统采用五层流水线架构，自下而上为数据层、信号层、决策层、执行层、复盘层，层间通过本地SQLite数据库与消息推送单向衔接：

```
┌───────────────────────────────────────────────────────┐
│ 复盘层  自动复盘引擎 · trade_case案例库 · 每周复盘报告   │  ← 第5章
├───────────────────────────────────────────────────────┤
│ 执行层  纪律强制执行器R1-R6 · 卖出风控T1-T4 · 条件单     │
│         （券商条件单 → miniQMT → 全自动，通道可插拔）    │  ← 第4章
├───────────────────────────────────────────────────────┤
│ 决策层  买入8条件评分卡（≥4条=全仓信号）                 │
│         观察池六态状态机（候选→观察→可买→持仓→卖出→归档）│  ← 第3章
├───────────────────────────────────────────────────────┤
│ 信号层  事件驱动引擎（DeepSeek抽取事件→规则映射板块      │
│         →成分股白名单校验，三段式防幻觉）                │  ← 第3章
├───────────────────────────────────────────────────────┤
│ 数据层  多源冗余采集（akshare/tushare/baostock/RSSHub） │
│         SQLite六表落库 · 健康检查 · 故障降级"仅观察"     │  ← 第2章
└───────────────────────────────────────────────────────┘
   横向设施：n8n工作流调度 · 钉钉机器人L1/L2/L3分级告警
```

各层职责如下表所示，层与层之间只通过数据库表和标准消息格式通信，任何一层可独立替换实现。

| 层 | 核心职责 | 输入 | 输出 | 详细设计 |
|---|---|---|---|---|
| 数据层 | 多源采集行情/涨停池/板块/资金流/快讯，落库并做健康检查与故障降级 | akshare、tushare、baostock、RSSHub快讯 | SQLite六张表（daily_quote等）+降级标记 | 第2章 |
| 信号层 | 从快讯中抽取事件，三段式防幻觉映射出受益个股候选集 | news_event表+DeepSeek V4-Flash | 事件候选股清单（已过白名单校验） | 第3章 |
| 决策层 | 买入8条件量化评分，驱动观察池六态状态机流转 | 六表数据+候选股清单 | 当日交易计划卡（9:15前推送） | 第3章 |
| 执行层 | 纪律强制执行（R1-R6）与卖出风控（T1-T4），下发条件单 | 交易计划卡+实时/准实时监控 | 条件单指令+钉钉L1/L2/L3告警 | 第4章 |
| 复盘层 | 收盘后自动复盘、案例入库、周报生成 | 成交记录+当日数据快照 | trade_case案例库+每周复盘报告 | 第5章 |

架构设计的第一原则是**信号层与执行层解耦、执行通道可插拔**：直接原因是资金门槛约束（3.25万元不满足官方QMT最低10万元门槛，来源：licai.cofool.com，2026-06），现阶段只能用零门槛的券商条件单，但本金增长或门槛核实后可平滑切换到miniQMT，信号与决策层代码零改动。第二原则是**宁可漏信号、不可错信号**：数据层任一关键源失效时，当日信号自动降级为"仅观察"并钉钉告警，绝不在残缺数据上生成买入建议（第2章降级策略）。集合竞价时段（9:15—9:30）只采集数据、不出信号，直接回应1.1中"被集合竞价洗盘吓卖"的教训。

## 第2章 数据层设计

数据层是整个系统的地基，也是当前环境下风险最高的一层。2025—2026年免费爬虫生态持续劣化：东方财富自2025年起大幅升级反爬（封IP、验证码），社区共识为"批量爬虫路线不可持续"；北向资金自2024-05-13起取消盘中实时披露、2024-08-19起仅盘后披露成交总额与十大活跃股（来源：新浪财经，2024-08-18；quant.10jqka.com.cn，2026-06）。因此本章设计遵循三条原则：多源冗余（任何单一接口失效不导致系统停摆）、本地落库（所有数据进SQLite，历史可回溯、可复算）、故障降级（数据缺失时信号自动降级为"仅观察"并钉钉告警，绝不基于残缺数据生成操作信号）。

### 2.1 数据源选型矩阵

下表对四个候选数据源按实时性、稳定性、成本与用途进行对比，选型结论为"akshare为主研究源、tushare日线兜底、baostock做回测底座、RSSHub自建快讯"。

| 数据源 | 实时性 | 稳定性 | 成本 | 定位与用途 |
|---|---|---|---|---|
| akshare | 东财网页快照，延迟数秒 | 中低：2025年起东财反爬升级，接口可能随时失效 | 免费 | 涨停池、跌停池、龙虎榜、主力资金流（东财大单口径）、板块题材——适合研究，不宜实盘依赖 |
| tushare Pro | 日线（50次/分限频） | 高：官方维护、数据规范 | 120积分免费仅日线；2000积分≈200元/年；分钟线/新闻需单独付费 | 日线行情兜底与交叉校验 |
| baostock | 无实时行情；分钟线当日20:00入库 | 高 | 免费 | 日/分钟历史K线，回测数据底座 |
| RSSHub自建+东财快讯爬取+akshare全球快讯 | 分钟级（取决于轮询频率） | 中：自建路由可控，爬取端点受反爬影响 | 免费（服务器自备） | 财经快讯事件流，喂给事件驱动引擎 |

（来源：tushare.pro官方文档doc_id=290；pypi.org/project/baostock，2026-07；github.com/ourongxing/newsnow issues#355，2026-06）

矩阵取舍说明：不选efinance，因其自2025年上半年起受东财匿名调用限制、维护放缓（来源：知乎专栏，2025）；不选财联社第三方镜像，因旧端点已404失效，故以RSSHub自建路由为主、东财快讯限速爬取为辅、akshare全球快讯兜底。akshare接口最全，但本质是东财网页爬虫，反爬收紧时最先失效，故只承担"增强信号"职责，其专属数据缺失不允许阻断日线级基础流程。tushare免费档仅日线，对"盘前准备+盘后复盘"场景已够用，暂不升级；分钟级数据由baostock当日20:00后补齐，仅供复盘与回测。

### 2.2 多源冗余与降级策略

针对两类结构性风险（东财反爬、北向停披）与常规接口故障，设计如下降级策略表。降级动作由数据层的健康检查模块自动执行：每次采集任务完成后校验记录数与字段完整率，不达标即触发对应降级分支。

| 故障场景 | 检测口径 | 降级动作 | 信号影响 |
|---|---|---|---|
| akshare涨停池/板块接口被反爬（封IP、验证码） | 连续2次请求失败或返回为空 | 切换备用User-Agent与限速（≥3秒/次）；仍失败则用tushare日线涨跌幅≥9.8%近似涨停池 | 涨停家数类条件标记"数据降级" |
| akshare主力资金流失效 | 字段完整率<90% | 停用资金流条件，等待恢复 | 当日信号降级为"仅观察"+钉钉告警 |
| 北向资金盘中停披（2024年起结构性变化） | 永久状态，非故障 | 用东财主力资金（大单口径）+行业ETF资金流替代北向口径 | 资金轮动判断改用替代指标 |
| 快讯源全部失效 | 30分钟无新增快讯 | RSSHub→东财爬取→akshare全球快讯三级切换；全失败则暂停事件驱动 | 事件类买入条件（第8条）记0分并告警 |
| tushare积分/限频超限 | 返回限频错误码 | 当日日线改用akshare快照收盘后落库，次日补校验 | 不影响，仅延迟落库 |

降级策略的逻辑是"宁可漏信号，不可错信号"：买入8条件中有4条依赖akshare专属数据（板块涨幅前5、涨停家数、资金承接、事件催化），数据残缺时评分卡区分度失真，继续生成买入建议的危害大于暂停信号，故统一降级为"仅观察"并钉钉告警。北向替代方案需注意口径差异：东财主力资金为大单口径，与北向"外资持股"口径不同源，仅作资金轮动的代理变量而非等效替代，信号层应降低该条件权重（第3章评分卡体现）。

### 2.3 数据表设计（SQLite）

存储选型为SQLite 3：单机零部署、单文件易备份、日增数据量千行级远低于其性能上限。共6张核心表，覆盖第3章信号层所需的全部输入：日线行情、涨停池、板块涨幅、资金流、新闻事件、观察池状态。

```sql
-- 日线行情：tushare主源，akshare兜底；backfill标记降级数据
CREATE TABLE daily_quote (
    trade_date   TEXT NOT NULL,            -- 交易日 YYYY-MM-DD
    ts_code      TEXT NOT NULL,            -- 股票代码 如 600519.SH
    open REAL, high REAL, low REAL, close REAL,
    pct_chg      REAL,                     -- 涨跌幅 %
    vol          REAL,                     -- 成交量（手）
    amount       REAL,                     -- 成交额（千元）
    turnover     REAL,                     -- 换手率 %
    source       TEXT DEFAULT 'tushare',   -- tushare/akshare/baostock
    backfill     INTEGER DEFAULT 0,        -- 1=降级/补录数据
    PRIMARY KEY (trade_date, ts_code)
);

-- 涨停池：akshare stock_zt_pool_em，每日盘后快照
CREATE TABLE limit_pool (
    trade_date   TEXT NOT NULL,
    ts_code      TEXT NOT NULL,
    name         TEXT,
    limit_times  INTEGER,                  -- 连板数
    first_time   TEXT,                     -- 首次封板时间
    last_time    TEXT,                     -- 最后封板时间
    open_times   INTEGER,                  -- 炸板次数（衡量承接）
    sector       TEXT,                     -- 所属板块（东财口径）
    degraded     INTEGER DEFAULT 0,        -- 1=tushare近似推算
    PRIMARY KEY (trade_date, ts_code)
);

-- 板块日线：买入条件1/2（涨幅前5、涨停家数增加）的数据基础
CREATE TABLE sector_daily (
    trade_date   TEXT NOT NULL,
    sector_name  TEXT NOT NULL,            -- 东财板块名
    pct_chg      REAL,                     -- 板块涨幅 %
    rank_no      INTEGER,                  -- 当日板块涨幅排名
    up_count     INTEGER,                  -- 上涨家数
    limit_count  INTEGER,                  -- 涨停家数
    amount       REAL,                     -- 板块成交额
    etf_code     TEXT,                     -- 关联行业ETF（北向替代用）
    PRIMARY KEY (trade_date, sector_name)
);

-- 资金流：东财主力资金大单口径；北向停披后的代理变量
CREATE TABLE capital_flow (
    trade_date   TEXT NOT NULL,
    ts_code      TEXT NOT NULL,            -- 个股或ETF代码
    main_inflow  REAL,                     -- 主力净流入（万元）
    super_large  REAL,                     -- 超大单净流入
    large        REAL,                     -- 大单净流入
    source       TEXT DEFAULT 'akshare',
    PRIMARY KEY (trade_date, ts_code)
);

-- 新闻事件：快讯落库+LLM打标结果，事件驱动引擎输入
CREATE TABLE news_event (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    pub_time     TEXT NOT NULL,            -- 发布时间
    source       TEXT,                     -- rsshub/eastmoney/akshare
    title        TEXT,
    content      TEXT,
    llm_sectors  TEXT,                     -- LLM提取的受益板块 JSON数组
    llm_score    REAL,                     -- 事件重要度评分 0-10
    verified     INTEGER DEFAULT 0,        -- 1=已通过板块白名单校验
    created_at   TEXT DEFAULT (datetime('now','localtime'))
);

-- 观察池：买入8条件评分卡状态机，第3章核心表
CREATE TABLE watch_pool (
    ts_code      TEXT NOT NULL,
    add_date     TEXT NOT NULL,            -- 入池日期
    sector_name  TEXT,
    cond_score   INTEGER DEFAULT 0,        -- 当前满足条件数（满分8）
    status       TEXT DEFAULT 'candidate', -- candidate/watching/buyable/holding/exited/archived
    buy_date     TEXT,                     -- 买入日（触发后回填）
    exit_reason  TEXT,                     -- 出池原因
    updated_at   TEXT,
    PRIMARY KEY (ts_code, add_date)
);
```

表结构设计有三处取舍。其一，行情类表以(trade_date, ts_code)复合主键天然防重，配合INSERT OR REPLACE容忍调度器重跑，免除额外幂等逻辑。其二，source/backfill/degraded字段是降级策略在数据层的落点：评分卡读取时可直接过滤或降权降级数据，保证数据质量信息不在层间传递中丢失。其三，watch_pool采用单表状态机而非多表拆分——3万本金场景下持股不超过2只、观察池预计不超过30只，单表足以承载。SQLite单文件每日收盘后自动备份至网盘目录，备份成本为零。

### 2.4 调度时序

调度器采用APScheduler（Python进程内cron），部署于闲置电脑或低配云主机。时序设计直接服务短线操作场景：用户实际成交集中在09:25—09:56早盘时段，且曾在9:15—9:25集合竞价阶段被主力洗盘手法（挂单价±10%制造恐慌）干扰心态而错误卖出，因此集合竞价时段的定位是"只采数据、不生成任何操作信号"，竞价异动仅作记录，供9:30后由信号层结合量能综合判断。

| 时段 | 时间 | 任务 | 数据源 | 输出 |
|---|---|---|---|---|
| 盘前 | 08:30 | 拉取隔夜外盘/商品（WTI、黄金、美元指数）、快讯增量、LLM事件打标 | akshare全球快讯+RSSHub | news_event更新、盘前事件简报推送钉钉 |
| 集合竞价 | 09:15—09:25 | 每2分钟采集竞价快照（价格、匹配量），仅落库不出信号 | akshare快照 | 竞价异动记录；09:25竞价结果（高开/低开幅度）写入简报（集合竞价采集窗口；信号锁定期为9:15–9:30，见第4章R1） |
| 盘中 | 09:30—15:00 | 每5分钟轮询板块涨幅榜与观察池个股；10:00/13:30/14:30三次板块排名快照 | akshare（限速≥3秒） | sector_daily增量、观察池条件实时更新 |
| 盘后① | 15:30 | 涨停池、主力资金流、板块日线落库；tushare日线兜底校验 | akshare+tushare | limit_pool/capital_flow/sector_daily/daily_quote |
| 盘后② | 20:00 | baostock分钟线补库；执行降级健康检查；生成当日复盘数据包 | baostock | 分钟K线落库、降级告警、复盘简报 |

时序安排有两点依据。第一，盘中轮询定为5分钟而非实时：东财快照本身延迟数秒，高频请求会加速封IP，5分钟粒度对"板块涨幅前5"这类分钟级不敏感条件已足够，日请求量控制在百次级。第二，盘后拆为15:30与20:00两批：baostock分钟线当日20:00才入库（来源：pypi.org/project/baostock，2026-07），合并会迫使涨停池等关键数据延后；且15:30批次若发现akshare数据残缺，20:00批次尚有补救重试窗口，与2.2节健康检查形成闭环。

## 第3章 信号层：交易体系工程化

第2章的数据层已经把行情、涨停、板块、资金、快讯五类数据落进 SQLite 的 `daily_quote`、`limit_pool`、`sector_daily`、`capital_flow`、`news_event`、`watch_pool` 六张表，信号层的任务只剩两件：把用户的"七步分析框架"编译成一条可定时运行的事件驱动流水线，把"买入8条件"编译成一张每格都能用 SQL 算出来的评分卡。本章只负责买入侧与观察池；买入信号产出"交易计划卡"后，持仓期的卖出风控交由第4章的纪律执行器接管。

### 3.1 七步分析框架 → 事件驱动引擎流水线

七步框架中真正需要自然语言理解的只有第①步"宏观逻辑"（世界发生了什么、哪些资产受益），这一步交给 DeepSeek；其余六步全部是确定性计算：第②步资金轮动读 `capital_flow` 表的板块净流入环比，第③⑤步行业与板块验证读 `sector_daily` 的上涨家数/成交额和 `limit_pool` 的涨停计数，第④步商品验证（WTI、天然气、美元指数、黄金、VIX）由 akshare 商品与外盘行情接口按同一调度落库后比对方向，第⑥步个股筛选即 3.2 节的评分卡，第⑦步持有逻辑落到 `watch_pool` 的状态机（见 3.3）。一句话概括设计原则：**LLM 只负责把快讯变成结构化事件，其余环节全是 SQL 与规则引擎**。

```
┌─────────────┐   ┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐   ┌─────────────┐
│ ① 快讯采集   │→ │ ② DeepSeek       │→ │ ③ 受益链映射      │→ │ ④ 成分股白名单    │→ │ ⑤ 观察池入库 │
│ RSSHub自建   │   │ 结构化抽取        │   │ 事件→商品→板块    │   │ 校验（防幻觉）    │   │ watch_pool  │
│ +财联社快讯  │   │ 事件/方向/强度    │   │ 规则表→候选个股   │   │ akshare板块成分股 │   │ 状态=候选    │
└─────────────┘   └──────────────────┘   └──────────────────┘   └──────────────────┘   └─────────────┘
      │ 盘前6:00-8:00 / 盘后15:30批量       │ 板块词表人工维护        │ 不在白名单内一律丢弃   │ 写入news_event
      ▼                                    ▼ （种子=8月关注方向）    ▼ 拦截并记日志          ▼ 与watch_pool
   失败降级：当日信号                        具身智能/人形机器人、      幻觉股在此被拦截
   全部降为"仅观察"                          固态电池、半导体封装、
                                            光通信
```

防幻觉是本节的硬约束。LLM 事件驱动选股的已知陷阱是幻觉虚构个股与事件的关联（来源：LLM选股实践调研，2025–2026年），因此受益股映射采用三段式：**第一段** DeepSeek 只抽取事件要素，输出的 JSON schema 中根本不设股票代码字段，从接口层面杜绝 LLM 直接荐股；**第二段** 用人工维护的"事件关键词→板块"规则表做映射，板块词表的种子直接取用户8月关注方向（具身智能/人形机器人——宇树、智元及核心供应商、固态电池（用户已否决方向，保留作监控对照）、半导体先进封装/设备、光通信（用户已否决方向，保留作监控对照）），后续按复盘增删；**第三段** 调用 akshare 板块成分股接口拉取实时成分股白名单，规则映射产出的候选个股凡不在白名单内一律拦截并记日志。这样即使规则表写错或行情软件改了板块归属，错误也止于一只候选股被丢弃，而不会污染观察池。需提示：akshare 财联社快讯接口的长期可用性待验证（来源：交叉验证简报，2026年），故采集层保留 RSSHub 自建快讯作为降级通道，与第2章的多源冗余策略一致。

成本方面，DeepSeek V4-Flash 输入 1 元/百万 token（缓存命中 0.02 元）、输出 2 元/百万 token（来源：api-docs.deepseek.com/quick_start/pricing，2026-07核实）。按每日 50 条快讯、单条输入约 2000 token、输出约 500 token 估算，50 条/日 ×（2000×1 元 + 500×2 元）/百万 ≈ 0.15 元/日；抽取任务错峰执行并命中缓存后，年成本约 40–55 元，与第6章"月 1–5 元、年≤60 元"的估算口径互相咬合。官网已预告峰谷定价（9:00–12:00、14:00–18:00 高峰 2 倍，生效日期待验证），因此抽取任务统一排在盘前 6:00–8:00 与盘后 15:30 批量执行，天然避开高峰时段。

DeepSeek 抽取的 prompt 与输出 schema 如下，要点是用 `response_format=json` 强制结构化输出，并在 schema 注释中明确"禁止输出股票代码"：

```python
import json, requests

SYSTEM_PROMPT = """你是A股事件抽取器。从输入快讯中抽取市场事件，只输出JSON，禁止输出任何股票代码或个股名称。
字段定义：
- event_type: 事件类型，枚举[地缘政治/政策/行业动态/公司公告/商品异动/技术突破]
- direction: 对相关板块的影响方向，枚举[利好/利空/中性]
- strength: 事件强度1-5，5=重大（如战争、国家级政策）
- sectors: 受益或受损的行业板块名称数组（用通用行业名，如"石油开采"，禁止写个股）
- commodities: 关联商品数组（如"WTI原油"，无则空数组）
- summary: 一句话事件摘要（≤40字）
没有有效事件时输出 {"events": []}"""

def extract_events(news_text: str) -> dict:
    resp = requests.post(
        "https://api.deepseek.com/chat/completions",
        headers={"Authorization": f"Bearer {DEEPSEEK_API_KEY}"},
        json={
            "model": "deepseek-v4-flash",
            "messages": [
                {"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": news_text},
            ],
            "response_format": {"type": "json_object"},
            "temperature": 0.1,   # 抽取任务用低温，抑制发散
        }, timeout=30)
    return json.loads(resp.json()["choices"][0]["message"]["content"])

# 输出示例（对应"特朗普打击伊朗"案例）：
# {"events": [{"event_type": "地缘政治", "direction": "利好", "strength": 5,
#             "sectors": ["石油开采", "油服工程"], "commodities": ["WTI原油", "天然气"],
#             "summary": "美伊冲突升级，霍尔木兹海峡通航风险推高油价"}]}
```

### 3.2 买入8条件 → 量化评分卡

评分卡把笔记中"满足4条以上才允许全仓买入"的八条主观条件逐条翻译成"数据表字段→计算式→阈值"三要素。其中条件5依赖昨日K线数据，标注为盘前校验项；条件6依赖盘中分钟级缓存，标注为盘中校验项——条件5的盘前标注与笔记"次日没有高开低走"本身的时序含义一致，不是系统缺陷而是规则本来的约束。

| # | 笔记原文 | 数据来源 | 计算式 | 触发阈值 | 校验时段 |
|---|---|---|---|---|---|
| 1 | 板块当天涨幅前5 | `sector_daily` | 当日板块涨幅排名 `rank()` | rank ≤ 5 | 盘中/盘后 |
| 2 | 板块涨停家数增加 | `limit_pool` | 板块涨停计数环比 | 今日 > 昨日 | 盘后（盘中为实时计数） |
| 3 | 前排不是后排 | `daily_quote`+`sector_daily` | 个股成交额在板块内分位 | 分位 ≥ 80%（前20%） | 盘中/盘后 |
| 4 | 放量突破或涨停承接 | `daily_quote`+`limit_pool` | 量比≥2 且收盘创20日新高；或炸板后回封且封单额≥5000万 | 满足其一 | 盘后 |
| 5 | 次日没有高开低走 | `daily_quote` | 排除：高开（open/昨收−1 > 2%）且低走（close < open） | 昨日K线不满足该排除式 | 盘前校验 |
| 6 | 破分时均价线能快速拉回 | 分钟行情（盘中缓存） | 价格低于 VWAP 的持续时长 | ≤ 15 分钟且收回 VWAP 上方 | 盘中校验 |
| 7 | 大盘红盘数改善 | `daily_quote` 全市场 | 上涨家数环比 | 今日上涨家数 > 昨日 | 盘中/盘后 |
| 8 | 有明确事件/政策/中报催化 | `news_event` | 3.1 引擎输出中该股所属板块存在 strength ≥ 3 的利好事件 | 近3个交易日内存在 | 盘前/盘后 |

> 注：大纲口径"量比+换手率"中，换手率由量比与成交额分位替代（量比本身即换手率与历史均值的比值，避免重复计权）。

解读：八条口径里有三处刻意的"保守化"取舍。其一，条件3用成交额分位而非涨幅分位定义"前排"，因为笔记中"前排=有逻辑支撑的高辨识度股"，成交额是市场用真金白银投票的辨识度指标，涨幅前排反而可能混入后排补涨股——这正是用户复盘里"买后排补涨"的亏损模式。其二，条件4的封单额阈值5000万是按用户3.25万本金、只做10元上下低价股的流动性环境设定的经验初值，需在回测阶段用第5章的方法校准，不宜直接当定论。其三，条件8的 strength≥3 与"近3日"窗口，对应笔记中"事件当天追高"的教训：事件催化必须在启动初期确认，超过3日的旧事件不计分，从规则上封堵利好兑现日的追买。集合竞价时段（9:15–9:30）评分引擎整体休眠、不生成任何操作信号——用户曾被竞价阶段主力洗盘吓出筹码，该锁定期的纪律执行细节见第4章。

触发规则按笔记原文硬编码：满足条件数 ≥4 生成"全仓买入信号"并产出交易计划卡（卡片字段与确认流程由第4章详述）；2–3 条仅把标的在观察池中标为"观察（WATCHING）"、继续跟踪；<2 条不动作。核心伪代码：

```python
def score_candidate(stock, ctx):
    """ctx: 当日数据上下文（sector_daily/limit_pool/daily_quote/news_event等）"""
    checks = {
        "c1_sector_top5":      ctx.sector_rank(stock.sector) <= 5,
        "c2_limit_up_incr":    ctx.limit_count(stock.sector, "today")
                               > ctx.limit_count(stock.sector, "yesterday"),
        "c3_front_runner":     ctx.amount_pct_in_sector(stock) >= 0.80,
        "c4_volume_breakout":  (ctx.volume_ratio(stock) >= 2
                                and ctx.close(stock) >= ctx.high_20d(stock))
                               or ctx.resealed_with_amount(stock, 50_000_000),
        "c5_no_open_high_fade": not ctx.gap_up_then_fade(stock, gap=0.02),
        "c6_vwap_recover":     ctx.below_vwap_minutes(stock) <= 15
                               and ctx.close(stock) >= ctx.vwap(stock),
        "c7_breadth_improve":  ctx.advancers("today") > ctx.advancers("yesterday"),
        "c8_catalyst":         ctx.has_event(stock.sector, min_strength=3, days=3),
    }
    n = sum(checks.values())
    if in_call_auction(now()):          # 9:15-9:30 锁定期
        return Signal("NONE", checks)   # 不生成任何操作信号
    if n >= 4:
        return Signal("FULL_BUY", checks, card=build_trade_plan(stock, checks))
    if n >= 2:
        return Signal("WATCH", checks)  # watch_pool 状态置为"观察（WATCHING）继续跟踪"
    return Signal("NONE", checks)
```

### 3.3 观察池管理：生命周期状态机

`watch_pool` 表中的每条记录带一个 `status` 字段，取值与迁移条件如下表。状态机把笔记里分散的"先加自选""千万不要急着乱买""逻辑失效即卖出"收敛成一张可自动执行的迁移图。

| 状态 | 进入条件 | 退出迁移 | 责任模块 |
|---|---|---|---|
| 候选 CANDIDATE | 事件引擎入库（白名单校验通过）；或手动加自选 | 评分≥2 → 观察；14日无评分≥2 → 归档 | 3.1 引擎 |
| 观察 WATCHING | 评分命中2–3条 | 评分≥4 → 可买；逻辑失效（strength≥3利空或板块跌出前15）→ 归档 | 3.2 评分卡 |
| 可买 BUYABLE | 评分≥4，生成交易计划卡 | 用户确认执行 → 持仓；计划卡过期（T+1未执行）→ 回退观察 | 3.2 + 第4章确认器 |
| 持仓 HOLDING | 交易计划卡被确认执行 | 触发第4章卖出规则 → 卖出；逻辑失效 → 卖出 | 第4章风控（接口预留） |
| 卖出 EXITED | 卖出委托成交回报 | 当日收盘后 → 归档（写入复盘标签） | 第4章 |
| 归档 ARCHIVED | 任一状态的终止态 | 只读，供第5章回测与复盘统计 | 复盘模块 |

解读：状态机有两个为第4章预留的关键接口。一是 BUYABLE→HOLDING 必须经过"交易计划卡确认"而不是信号直连委托，这保证半自动执行通道（券商条件单+人工确认）下每一次建仓都有书面化的买点卖点记录，落实笔记"操作前先写下买点和卖点"。二是 HOLDING 状态不内嵌任何卖出逻辑，只暴露 `logic_invalid`（逻辑失效）与 `risk_trigger`（风控触发）两个出口事件，卖出规则全部归属第4章——这样买入侧与卖出侧可以独立迭代，修改止损规则不会触碰评分卡。14日与 T+1 两个过期计时器则对应笔记"没机会就先加自选"的反面：观察池不是股票坟场，长期无信号的标的自动归档，防止池子膨胀稀释注意力。

### 3.4 手写规则 → 系统实现对照表

下表把笔记第六、七节的原始心得逐条映射到本章机制，并说明每条系统化的防呆价值。

| 笔记原文 | 系统实现 | 防呆价值 |
|---|---|---|
| "满足4条以上才允许全仓买入" | 评分卡 n≥4 才发 FULL_BUY（3.2） | 把模糊的"感觉够了"变成可审计的计数 |
| "没机会就先加自选，千万不要急着乱买（易亏损）" | n<2 不动作；CANDIDATE 状态只看不买（3.3） | 从流程上删除"手痒单"的入口 |
| "忘记看板块排行榜"（错过一鸣食品） | 盘前/盘后任务自动输出 sector_daily 涨幅榜与涨停榜推送 | 每日扫描不依赖记忆，消灭"错过"类错误 |
| "不看9:15–9:30的分时K线" | 集合竞价锁定期，评分引擎休眠不推信号（3.2） | 主力竞价洗盘无法触发任何情绪化操作 |
| "只买前排，错过就空仓；不买后排补涨" | 条件3成交额分位≥80%，不满足则该条不得分（3.2） | 后排股天然难凑够4分，空仓成为默认结果 |
| "事件当天追高"（机器人大会利好兑现） | 条件8限定事件窗口≤3日，旧事件不计分（3.2） | 利好兑现日买入被规则封堵 |
| 高位买壹连科技，违反"不买创业板"纪律 | 候选池黑名单过滤 300/688 开头代码（白名单校验环节） | 违反板块纪律的股票进不了观察池 |
| "操作前，先写下买点和卖点" | 交易计划卡强制含买点/卖点字段，未填不可确认（3.3接口，第4章详述） | 把自律要求变成表单必填项 |

解读：对照表揭示了手写体系与系统化的本质差异——笔记中的纪律是"提醒自己不做什么"，依赖当时的心态状态；系统实现是"让错误操作在流程里走不通"，不依赖心态。用户两笔亏损（通源石油追高接回 −2.4%、壹连科技 −3.9%）分别对应表中"事件追高/情绪化接回"与"黑名单过滤"两行，恰好都是纯执行错误而非判断错误，这类错误最适合用状态机和黑名单这类结构性手段消除。需要客观说明的是，系统化只能消除执行层错误，条件4阈值、strength 评分这类判断参数仍需第5章回测校准，本章交付的是"规则不再被违反"的机制，而非"规则本身正确"的证明。

## 第4章 风控与执行层

本章接管观察池状态机的"持仓→卖出"阶段，解决用户实盘记录中最尖锐的问题：**风控与纪律早已写在笔记里，但盘中情绪一来就执行不到位**。设计原则是"人只负责确认，监控和拦截交给系统"。考虑到用户操作窗口几乎全部集中在09:25–09:56（券商成交记录印证），当日**交易计划类**推送须在9:15前完成，为其预留上班前的决策余量；风控告警（T1–T4/L1–L3）按各自时点推送。

### 4.1 卖出风控四触发自动监控

用户石油案例的四条风控触发条件中，有两条当时未执行（来源：用户交易笔记，2026-07）。系统将其转化为常驻监控任务，把"靠自律"变成"靠推送"。

| # | 触发条件 | 数据口径（可计算定义） | 监控频率 | 告警动作 |
|---|---|---|---|---|
| T1 | 停火类事件（持仓逻辑失效事件） | news_event表中命中"停火/和解/协议"关键词且与持仓主线事件冲突；由LLM判定"逻辑失效=是/否"，人工复核后生效 | 快讯到达即触发 | L3：钉钉+@，建议减仓50% |
| T2 | 持仓板块跌破5日线 | sector_daily表：板块指数收盘价 < MA5（最近5个交易日收盘均价），以14:55快照为准 | 每日14:55 | L2：钉钉，建议减仓30% |
| T3 | 板块龙头跌停 | limit_pool跌停池：持仓板块涨幅贡献前1的成分股出现在当日跌停池（14:50快照，避免尾盘异动误判） | 盘中每5分钟 | L3：钉钉+@，建议清仓 |
| T4 | 布油连跌2日+板块资金连出2日 | 布伦特原油连续2个交易日收跌（akshare商品接口，研究源口径），且capital_flow表该板块主力净流入连续2日为负；两条件**同时**满足才触发 | 每日收盘后 | L3：钉钉+@，建议清仓 |

四条触发的严格程度做了区分：T4采用双条件交叉验证（商品价格与资金流同时恶化才触发），因为用户正是靠这条规则在石油案例中成功逃顶，单条件误报会稀释L3告警的公信力。T1交给LLM判定而非关键词匹配，因"停火"类措辞在快讯中变体多、关键词漏报率高；但LLM判定必须人工复核后才转为卖出建议，防止幻觉触发误操作。T3取"涨幅贡献前1"对应笔记"龙头跌停"的原始语义，避免跟风股跌停的噪音。

告警分三级：**L1观察**仅进盘后日报；**L2注意**（T2类）盘中钉钉普通消息；**L3立即行动**（T1/T3/T4类）钉钉消息+@本人，并需在回执链接中点选"已执行/放弃并填理由"，未回执的L3在15:00前每20分钟重推一次——这是针对"两条触发未执行"教训的兜底。

### 4.2 纪律强制执行器

本节是本方案的灵魂。用户两笔实盘亏损（通源石油接回-2.4%、壹连科技-3.9%）都源于情绪操作和违反纪律，四笔盈利交易全部按体系执行（来源：用户交易笔记，2026-07）。强制执行器把六条纸面纪律改造成硬性拦截规则：**不满足纪律的交易计划不会被生成和推送**，从源头消除"盘中临时起意"。

| # | 规则 | 系统实现口径 | 对应的用户真实教训 |
|---|---|---|---|
| R1 | 9:15–9:30信号锁定期 | 不生成、不推送任何**新的盘中**买卖计划（盘前9:15前已生成并送达的交易计划卡可查看，但锁定期内不得据此下单）；持仓风控告警正常推送但标注"集合竞价时段，建议9:30后复核再操作" | 2026-07-30被9:15挂+10%→-10%的洗盘吓到，09:25以跌停恐慌价卖出壹连科技（-3.9%），笔记原话"临时决策未看本笔记（失败）"；其纪律"不看9:15–9:30分时K线" |
| R2 | 禁买名单 | watch_pool与计划生成器硬编码过滤：创业板（300开头）、科创板（688开头）默认禁买；配置文件可改，但修改需连改两次确认并写入日志 | 2026-07-29买入壹连科技（创业板，60.997→58.59，-3.9%），违反自己"不买创业板/科创板"纪律 |
| R3 | 后排拦截 | 买入计划仅允许生成板块内涨幅排名≤前N（默认N=3）的候选；不满足时推送降级为"观察，错过就空仓" | 笔记原话："主线强时只买前排，错过就空仓；不买临时冒出、无辨识度的后排" |
| R4 | 挂价规则 | 交易计划卡的卖出建议价=触发时现价×0.99（低1%）；买入建议价=现价×1.01；环境检查项提醒"仅使用5G，不用WiFi挂单" | 创新医疗开盘5%时挂低1分钱未成交（"吐血，下次低1%卖"）；曾因WiFi网速慢导致卖单挂失败 |
| R5 | 交易计划卡强制生成 | 任何推送必须先生成计划卡（买点+卖点+仓位+失效条件），未生成卡片的股票一律不推送；卡片落库供第5章复盘评分 | 笔记原话："重要提醒：操作前，先写下买点和卖点" |
| R6 | 追高拦截 | 计划生成时校验：个股当日涨幅>7%且非计划内标的（不在watch_pool"可买"状态）→拒绝生成 | 笔记"最容易犯的两类纪律错误"之首：事件当天追高；通源石油7/20卖12.05后14:33以12.20追回，同日高接成本-210元 |

六条规则分两类：R2/R3/R5/R6为**硬拦截**（系统层无法绕过，修改需改配置文件并留痕），针对"明知故犯"型纪律错误；R1/R4为**软约束**（不阻止手工操作，通过推送时机和建议价口径引导），针对"执行环境"问题——系统无法也不应替用户锁死券商APP，只能让正确动作成为最顺手的动作。注意R1锁定期仍保留风控告警推送：锁定期防的是**主动情绪交易**，不是**被动风险应对**，两者不能混淆。

交易计划卡模板如下，由信号层在"可买→持仓"或风控触发时自动生成，推送前写入SQLite（供第5章复盘评分）：

```text
====== 交易计划卡 [2026-08-04 09:12] ======
标的：山东墨龙（002490）  方向：买入
所属板块：石油开采（当日板块涨幅排名：2/31 ✓前5）
触发信号：板块前5 + 涨停家数增加 + 前排 + 放量突破（4/8条件）

买点：≤8.10元（现价8.02×1.01）
仓位：25%（约8,000元，1,000股）
卖点：
  止损：跌破7.70元（-4.9%）或板块收盘破5日线
  止盈：冲高9.30元回落挂低1%卖（9.20元）
失效条件：T1停火类事件 / T3龙头跌停 / T4商品+资金双恶化
禁项核对：非创业板/科创板 ✓ 板块排名前3 ✓ 计划内标的 ✓
执行环境：5G网络，禁用WiFi挂单

=============================================
```

计划卡的"禁项核对"段是R2/R3/R6的可视化回执，用户能直接看到三条纪律全部通过；卡片不存在时，"没有卡片=不该操作"的判断成本接近于零。"失效条件"段把卖点从单一价格扩展为"价格+事件"双口径，对应其"逻辑失效即卖出"的总原则。

### 4.3 执行通道三阶段

执行通道的现实约束是资金门槛而非技术：官方miniQMT最低可验证开通门槛为国金证券10万元（来源：licai.cofool.com，2026-06），国盛证券另有5万元"小白版"（2025-10客户经理口径，待验证）。以3.25万元本金不具备官方程序化通道条件，故执行通道设计为可插拔三阶段，信号层与执行层解耦，切换通道不影响上游模块。

| 阶段 | 通道 | 触发条件 | 自动化程度 | 主要风险 |
|---|---|---|---|---|
| 现阶段 | 券商APP条件单（价格触发/止盈止损/回落卖出）+ 钉钉信号人工确认 | 当前（本金3.25万） | 半自动：系统出计划，人工在APP内设条件单 | 条件单有效期短（多数券商当日有效），需每日重设；网络依赖 |
| 中期 | miniQMT（xtquant） | 本金≥10万并完成券商开通，或5万档门槛经官方核实 | 自动下单，人工审批开关 | 需Windows常驻+QMT客户端在线；需履行程序化交易报告 |
| 远期 | 全自动（miniQMT+信号直连，条件单作为灾备） | miniQMT稳定运行≥3个月且复盘评分达标 | 全自动 | 误单放大风险，须保留每日限额与熔断 |

三阶段的核心取舍是"合规稳妥优先于自动化程度"：条件单零门槛、不触碰灰色接口，代价是每日9:15前需手工设置；GUI自动化（easytrader一类）年久失修，继任者jqktrader已于2024年停止维护并建议改用QMT/PTrade（来源：github.com/zsrl/jqktrader，2024-08），模拟点击有误单风险，本方案明确排除。远期阶段要求保留条件单作为灾备：单一通道失效（客户端掉线、券商维护）时，人工条件单是唯一能立刻接管的备份路径。

现阶段条件单参数设置示例（以计划卡为输入，在券商APP"智能条件单"中配置）：

| 参数 | 设置值 | 对应计划卡字段 |
|---|---|---|
| 条件单类型 | 价格条件单（卖出） | 止损/止盈 |
| 触发价 | 7.70元（止损）/ 9.20元（止盈） | 卖点 |
| 委托价 | 触发价×0.99（市价单亦可） | R4挂价规则：低1%确保成交 |
| 委托数量 | 1,000股（全仓） | 仓位 |
| 有效期 | 当日 | 计划有效期 |
| 回落卖出（备选） | 冲高9.30元后回落1%触发 | 止盈，锁利润 |

委托价统一采用"触发价×0.99"而非市价单：部分券商条件单不支持市价委托，且低1%的滑点成本（3万元本金约300元）远低于"没卖出去、次日低开"的机会成本。止损与止盈建议分设两张条件单，因多数券商APP的双向条件单一腿触发后不会自动撤另一腿，分设便于触发后人工核查。

**合规报告义务提醒**：凡"通过计算机程序自动生成或下达交易指令"即属程序化交易，使用自研自动化软件本身即触发报告义务，需通过券商向交易所报告（来源：湘财证券告知书，2025-07）。现阶段信号由人工转录为条件单、程序不直接下单，现阶段亦建议主动向券商报备；进入miniQMT阶段则**必须报备**。实质影响极小：高频认定标准为单账户每秒申报+撤单≥300笔或全日≥20000笔（沪深北交易所细则2025-07-07施行，来源：新华社，2025-04-07），本系统每日数次低频操作距此相差数个数量级，报备仅为手续性质，开通前联系券商客户经理办理并留存回执。

### 4.4 告警与推送

推送管道复用用户已有的n8n+钉钉机器人能力（其曾做过钉钉日报自动化），架构为三段式：

```text
[SQLite信号/风控事件] → n8n Webhook触发节点
    → 读取计划卡/告警内容 → （T1类事件先经DeepSeek API判定逻辑失效）
    → 按告警等级拼装消息 → 钉钉自定义机器人Webhook（L3附加@本人手机号）
    → 消息内嵌回执链接 → 用户点选"已执行/放弃+理由" → 写回SQLite告警回执表
```

流程仅需描述到节点类型：n8n的Webhook节点接收本地监控脚本的事件推送，HTTP Request节点调用DeepSeek API（仅T1类需LLM判定，控制token成本），再由钉钉机器人节点发送；回执链接是另一个Webhook，把用户决策写回数据库。回执数据是第5章复盘评分的数据源：系统只统计"告警后是否执行、执行偏差多大"，不统计盈亏——纪律评分评价的是执行质量而非市场运气。

钉钉L3告警消息模板（钉钉机器人markdown格式）：

```json
{
  "msgtype": "markdown",
  "markdown": {
    "title": "【L3】通源石油风控触发T4",
    "text": "## 🔴 L3 立即行动\n\n**标的**：通源石油（300164）（存量持仓示例；新买入受R2禁买创业板约束）持仓1,400股\n**触发**：T4 布油连跌2日 + 板块资金连出2日\n**建议动作**：全部卖出\n**建议挂价**：11.79元（现价11.91×0.99）\n**数据快照**：布油 78.2→76.9→75.4；主力净流入 -1.2亿/-0.8亿\n\n⏰ 锁定期提醒：当前9:26，属R1锁定期，建议9:30复核后操作\n\n[✅ 已执行](http://n8n.local/hook/ack?yes) ｜ [❌ 放弃（填理由）](http://n8n.local/hook/ack?no)\n\n@13800001111"
  },
  "at": { "atMobiles": ["13800001111"], "isAtAll": false }
}
```

模板有三处对应前文规则：挂价字段直接给出"现价×0.99"的计算结果（R4），避免盘中再做算术；锁定期提醒（R1）仅在9:15–9:30时段附加；回执链接把"执行/放弃+理由"固化为必填动作，放弃理由将作为复盘识别情绪操作的素材。L1/L2复用同一模板但去掉@与回执要求以降低告警疲劳——"狼来了"是推送系统最常见的失效模式，L3必须保持稀有（预期每周≤3次）才能维持响应敏感度。

## 第5章 复盘案例库与MVP路线图

前四章解决的是"盘中不出错"，本章解决"每周有进步"。用户方法论的核心判断是：积累二三十个案例后会发现，真正赚钱的案例只有少数几种，而亏钱的模式会反复出现，建立交易体系比单纯研究技术指标提升更快（来源：用户交易笔记，2026-07）。本章把"手写周记"升级为"系统自动生成、人工批注确认"的复盘闭环，并给出分四阶段的最小可行产品（MVP，Minimum Viable Product）落地路线。

### 5.1 自动复盘：成交对账→规则符合度评分→情绪操作标记

复盘的数据入口是券商成交记录对账：用户在券商APP导出交割单（CSV），或直接截图由OCR识别后人工核对，n8n定时任务将成交明细（代码、方向、价格、数量、时间）写入成交表，与第4章落库的交易计划卡、告警回执表做三方关联，即可对每笔交易自动计算**规则符合度评分**。评分设计为五维各20分、满分100，每个维度都对应第3/4章已定规则的可计算口径：

| 维度 | 判定口径（可直接写成代码） | 对应规则 | 分值 |
|---|---|---|---|
| S1 评分卡达标 | 买入当日该股8条件满足数：≥4得20；2–3得10；<2得0 | 第3章评分卡（n≥4才FULL_BUY） | 20 |
| S2 计划卡内交易 | 成交品种存在当日有效交易计划卡且plan_id可关联：是/否 | R5 计划卡强制 | 20 |
| S3 锁定期合规 | 主动买入/卖出成交时间 ≥ 09:30:00（风控T1–T4触发的被动卖出豁免） | R1 锁定期 | 20 |
| S4 禁买名单 | 代码不以300/688开头（与配置文件同步） | R2 禁买名单 | 20 |
| S5 挂价合规 | 卖出委托价 ≤ 委托时刻现价×0.99，或使用市价单 | R4 挂价规则 | 20 |

解读：五维评分刻意全部度量**执行质量**而非盈亏——一笔违反纪律却侥幸盈利的交易照样低分，一笔合规但被市场打脸的交易照样高分。这延续了第4章"纪律评分评价执行质量而非市场运气"的原则，防止"赚钱掩盖违规"强化坏习惯。S3的豁免条款区分主动与被动：风控告警触发的卖出在锁定期内操作不扣分，因为锁定期防的是情绪交易而非风险应对。用2026年7月实盘回测该评分表：山东墨龙（+8.1%）五维全过得100分；壹连科技买入违反S4（创业板60.997元建仓）且次日09:25集合竞价卖出违反S3，仅得60分——评分结果与笔记中"四笔按体系执行的都赚钱、两笔亏损都源于情绪操作"的定性结论完全一致（来源：用户交易笔记，2026-07）。

在评分之上，系统再打**情绪操作标记**（emotion_flag），每条标记给出可计算判定式：

| 标记 | 判定口径 |
|---|---|
| 计划外交易 plan_outside | 成交品种不在当日任何一张交易计划卡内（S2=0） |
| 锁定期操作 lock_period_op | 主动方向成交时间 < 09:30:00 |
| 追高买入 chase_high | 买入时个股当日涨幅 > 7% 且标的非计划内 |
| 同日高接 same_day_rebuy | 同一标的当日卖出后，以更高价格再次买入 |
| 告警未回执 alert_ignored | L3告警发出后未在当日点击回执，或未按建议动作执行 |

解读：五类标记直接对应笔记里反复出现的亏钱模式。"同日高接"的判定式（卖出价<同日买回价）能把通源石油7/20卖12.05元、14:33以12.20元接回、单日代价210元这类操作精确捕获（来源：用户交易笔记，2026-07）；"告警未回执"则把第4章回执数据反向用于复盘，未回执本身就是一条纪律证据。标记不评分、只计数：周度统计中某类标记出现≥2次即触发"该模式正在反复出现"的专题复盘，这正是"亏钱模式会反复出现"方法论的工程化。

### 5.2 案例库：trade_case表与每周复盘报告

案例库是第2章六表之外的第七张表（复盘模块私有，不影响信号链路）。一个"案例"定义为一次完整买→卖闭环（持仓未平则为开放案例），表结构如下：

```sql
CREATE TABLE trade_case (
    case_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    plan_id       TEXT,            -- 关联交易计划卡；NULL=计划外交易
    stock_code    TEXT NOT NULL,
    stock_name    TEXT NOT NULL,
    sector        TEXT,            -- 所属板块（sector_daily口径）
    buy_datetime  TEXT NOT NULL,   -- 精确到秒，用于锁定期判定
    buy_price     REAL NOT NULL,
    sell_datetime TEXT,            -- NULL=持仓中（开放案例）
    sell_price    REAL,
    shares        INTEGER NOT NULL,
    pnl           REAL,            -- 盈亏金额（未含佣金印花税，与笔记口径一致）
    pnl_pct       REAL,
    hold_days     INTEGER,
    score_n       INTEGER,         -- 买入当日8条件满足数（0-8）
    rule_score    INTEGER,         -- 五维规则符合度（0-100）
    emotion_flags TEXT,            -- JSON数组，如["chase_high","same_day_rebuy"]
    t_trigger     TEXT,            -- 卖出触发的风控编号T1-T4，NULL=人工卖出
    review_text   TEXT,            -- 人工批注：赚钱模式/亏钱模式归类
    created_at    TEXT DEFAULT (datetime('now','localtime'))
);
```

首批种子数据直接导入2026年7月实盘6笔波段：山东墨龙+8.1%、创新医疗+6.5%、金牛化工+3.8%、长城军工+3.4%（rule_score均为100，emotion_flags为空）；通源石油接回-2.4%（flags=["chase_high","same_day_rebuy"]）、壹连科技-3.9%（flags=["plan_outside","lock_period_op"]，S3/S4扣分）（来源：用户交易笔记，2026-07）。导入后即拥有6个已完成案例，距"二三十个案例"的样本门槛约需一个季度实盘积累。

每周复盘报告由n8n周日20:00定时生成，推送为钉钉长文档（钉钉开放平台文档API）或邮件，模板对齐用户手写周记习惯（其笔记按周记录"7月第四周目标+25%""8月第1周目标+25%"）：

```text
====== 周度复盘报告 [2026-08-03 ~ 2026-08-07] ======
一、收益对账
  本周收益：+4.2%（+1,365元）｜目标：+25%｜达成率：17%
  累计净值：1.042（本金33,865元）
二、交易统计
  完成案例：2个｜胜率：1/2（50%）｜平均盈亏比：+6.5% / -3.9%
三、规则符合度
  平均rule_score：80｜最低分案例：壹连科技（60分，S3锁定期+S4禁买扣分）
四、情绪操作清单（本周共2条）
  [lock_period_op] 07-30 09:25 壹连科技集合竞价卖出
  [plan_outside]   07-29 09:38 壹连科技买入（无计划卡）
五、典型案例复盘（系统自动生成骨架+人工批注）
  案例#6 壹连科技：买入无计划卡→竞价恐慌卖出，亏损3.9%
  模式归类：亏钱模式"事件追高+锁定期情绪操作"（历史出现第2次）
  下周改进项：R2禁买名单已硬拦截，无需人工注意
六、下周观察池
  状态=BUYABLE标的0个｜WATCHING 3个：……
==================================================
```

解读：报告第四节"情绪操作清单"与第五节"典型案例复盘"是方法论的直接载体——每笔亏损自动归类到"亏钱模式"，模式重复出现时计数器递增，用户能直观看到"哪几种错误在反复犯"。报告只自动填骨架，`review_text`字段保留人工批注入口，因为模式命名与归因仍需要人的判断；系统的价值在于把对账、统计、归档这些用户最不愿做的机械劳动降到零。

### 5.3 MVP路线图：P0–P3分阶段落地

全系统一次建成不现实，按"先跑通最小闭环、再逐层加固"分四个阶段，每阶段给出可测试的验收标准：

| 阶段 | 周期 | 目标 | 功能清单 | 验收标准（可测试） |
|---|---|---|---|---|
| P0 | 2周 | 板块监控+评分卡+钉钉推送 | 第2章daily_quote/sector_daily/limit_pool三表落库；3.2评分卡；9:15前钉钉推送评分结果 | 连续5个交易日9:15前收到评分卡推送；落库成功率≥95%（每日抽查缺数据≤1次/周） |
| P1 | 3周 | 事件引擎+风控告警 | DeepSeek快讯抽取（3.1流水线+白名单防幻觉）；T1–T4风控监控；L1/L2/L3分级告警与回执 | 快讯抽取JSON合法率≥90%（抽样50条）；构造测试数据触发T2–T4，告警5分钟内送达钉钉且回执可写库 |
| P2 | 2周 | 复盘库+周报 | trade_case表；交割单导入对账；五维评分与情绪标记；周日周报自动生成 | 导入7月14笔成交后自动生成6个已完成案例及1个开放案例（均瑶健康持仓未平）与首份周报；抽查3笔，rule_score与人工核算完全一致 |
| P3 | 远期 | 回测+miniQMT | baostock历史数据+backtrader自建事件回测（或聚宽在线分钟级验证）；本金达标后开通miniQMT | 评分卡规则在≥6个月历史数据上完成回测，输出胜率/盈亏比报告；回测通过且本金≥10万再谈程序化下单 |

解读：阶段排序的逻辑是"数据与信号先于风控、风控先于复盘、复盘先于回测"——P0先让数据可信，否则后续一切建立在沙地上；P2安排在P1之后，因为复盘评分依赖计划卡与告警回执数据。回测技术选型上，baostock免费日/分钟历史K线作数据底座（分钟线当日20:00入库，无实时行情，来源：pypi.org/project/baostock，2026-07），配合backtrader自建事件回测，或用聚宽在线平台做分钟级验证；qlib面向ML因子与截面选股、非事件驱动回测框架，不适合本体系的事件驱动短线场景（来源：dim01调研，2026-07）。需提示一句目标管理：周+25%的复利目标对应年化天文数字，长期不可持续，复盘报告中的"达成率"一栏应视为纪律执行的晴雨表而非收益KPI，建议随案例库积累逐步把目标改为"胜率与规则符合度"双指标。miniQMT官方可验证门槛为国金证券10万元（来源：licai.cofool.com，2026-06），以当前3.25万本金P3仅为预留接口，不构成近期任务。

### 5.4 事件日历机制：以8月机器人大会为例

笔记中"最容易犯的两类纪律错误"之首是事件当天追高，典型案例即2026年8月19日机器人大会：利好兑现，行情可能提前在8/10–8/17大涨，事件当天不追高（来源：用户交易笔记，2026-07）。系统设计事件日历表event_calendar（event_calendar 为六表之外的模块私有表），把这类"已知日期的预期事件"结构化为监控任务：

| 字段 | 含义 | 示例行（机器人大会） |
|---|---|---|
| event_date | 事件发生日 | 2026-08-19 |
| event_name | 事件名称 | 世界机器人大会 |
| sector | 关联板块 | 具身智能/人形机器人 |
| attn_start / attn_end | 提前关注窗口 | 2026-08-10 / 2026-08-17 |
| pre_action | 窗口期动作 | 正常按评分卡操作，跟踪前排 |
| day_action | 事件当天动作 | 不生成买入计划卡；持仓弹L2提示"利好兑现日，建议止盈" |
| status | 状态 | pending / active / expired |

解读：事件日历是第3章条件8（事件窗口≤3日）的补充——条件8管"旧事件不计分"，日历管"已知未来事件的行为预案"，两者一前一后封堵追高。机制上，attn_start到达时系统自动把关联板块前排标的批量加入观察池（CANDIDATE状态）；event_date当天计划生成器对该板块整体挂起（等效于该板块的临时R6），从流程上让"事件当天追高"无法发生。日历条目来源为人工录入（用户8月关注方向：具身智能/人形机器人、固态电池（用户已否决方向，保留作监控对照）、半导体封装、光通信（用户已否决方向，保留作监控对照），来源：用户交易笔记，2026-07），每条只需填一行，录入成本低于一次追高亏损的百分之一。

## 第6章 合规、成本与风险

前五章确定了纯自用定位、券商条件单半自动执行、DeepSeek V4-Flash事件引擎、SQLite本地库与n8n+钉钉推送的技术形态，本章为该方案兜底：先划清两条合规边界，再给出可执行的成本预算，最后登记必须正视的技术与投资风险。

### 6.1 合规边界：报告义务与荐股红线

本系统涉及两条监管线。第一条是程序化交易报告义务：《证券市场程序化交易管理规定（试行）》已于2024年10月8日施行，沪深北交易所实施细则于2025年7月7日施行（来源：新华社，2025-04-07）。凡"通过计算机程序自动生成或下达交易指令"即属程序化交易，个人投资者使用自研或定制自动化软件即触发报告义务，需通过开户券商向交易所报告（来源：湘财证券告知书，2025-07-04）。但高频认定的量化标准为单账户每秒申报与撤单合计≥300笔、或全日≥20000笔，交易所试运行显示触发异常监控的主要是量化私募与券商自营，中小个人投资者基本未发生相关情况（来源：新华社，2025-04-07）。本系统每日数次条件单远低于上述标准，实际后果仅是履行一次报备手续。

第二条是荐股红线，它决定了产品形态。《证券法》第120条规定，向他人提供证券分析、品种选择或买卖建议并直接或间接收取费用，即构成证券投资咨询业务，须经证监会核准，无资格者最高可罚500万元；个人自用、不对外提供建议、不收费则合法（来源：证监会微信公众号，2025-03-15）。广东证监局2024年11月查处的吴某平案中，当事人以公众号引流、微信群荐股收费，被没收255.17万元并处罚款200万元（来源：voc.com.cn，2024-11-15）；浙江证监局2025年12月查处的"金浤"案中，雪球大V公开荐股32只并反向卖出构成操纵市场，罚没各4162.39万元并处3年市场禁入（来源：hairunlawyer.com，2026-02）。即便选股结果由AI生成，收费推送给他人同样涉嫌非法荐股（来源：律师观点，2025-03）。

| 合规事项 | 规则口径 | 对本系统的影响 | 应对措施 |
|---|---|---|---|
| 程序化交易报告 | 使用自研自动化软件即触发报告义务；高频标准=每秒申报+撤单≥300笔或全日≥20000笔 | 低频条件单远低于高频标准，实质影响极小 | 启用前向开户券商履行报备手续，留存报告回执 |
| 非法荐股 | 对外提供选股建议并收费=投资咨询业务，须证监会核准，最高罚500万元 | 纯自用合法；任何收费推送、建群分享均越线 | 不建群、不收费、不对外推送信号；推送仅限本人钉钉 |
| 操纵市场 | 公开荐股后反向交易可构成操纵（"金浤"案） | 自用系统不公开发声即不涉此条 | 不在任何公开平台发布系统信号与持仓 |

解读：三条规则中真正约束设计的是荐股红线——它排除了"把信号卖给他人分摊成本"的商业模式，因此本系统从架构上就是单用户、单通道推送，钉钉机器人仅绑定本人账号。程序化交易报告的应对成本极低（一次券商报备），但不可省略：使用自研脚本生成交易信号本身即落入"自动化软件"口径，未报备在极端情况下可能被券商限制程序化接入。需要强调，"自用合法"的前提是资金与账户均为本人所有，代客理财、分仓操作不在本章讨论范围，也均超出合法边界。
